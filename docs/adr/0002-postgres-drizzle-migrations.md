# ADR 0002: PostgreSQL, Drizzle and migrations as a separate step

- Status: accepted
- Date: 2026-10-22

## Context

Sessions (and, later, messages) must survive restarts, and the rules that keep a conversation
consistent (one active turn, attempt fencing, idempotent sends) will be enforced by row locks,
unique constraints and conditional updates. The schema must evolve through reviewed migrations
that run exactly once even if two deploy steps overlap, the platform needs a readiness signal,
and tests need a real database without sharing state between test files.

## Options considered

- **Driver:** `postgres` (postgres.js) is fast and pleasant, but its connection model makes
  "one dedicated connection holds the migration lock" less direct. **node-postgres (`pg`)**
  gives a `Pool` for the API, a plain `Client` the migration runner owns, and per-connection
  options such as `statement_timeout`.
- **Query layer:** Prisma (generated client, its own migration engine and binary), Kysely
  (query builder only, migrations by hand). **Drizzle ORM** keeps SQL visible, types rows from
  the schema file, and drizzle-kit generates plain SQL migrations that are reviewed and committed.
- **When to migrate:** at API startup (every instance races; a failing migration takes the API
  down) vs **a one-shot step before the API starts** (compose `migrate` service, a platform's
  pre-deploy command).
- **Test database:** a shared local database (state leaks between runs), an in-memory fake
  such as pg-mem (no real locking), or **testcontainers** (the real PostgreSQL 17).

## Decision

- PostgreSQL 17 (`postgres:17.11-alpine`, digest pinned, the same image in tests and compose).
- `pg` pool wrapped by Drizzle's node-postgres adapter: `createDb()` returns
  `{ pool, drizzle, tx, close }`; the app receives it through `AppDeps` and never closes it.
- `src/db/schema.ts` is the source of truth; `drizzle-kit generate` writes `drizzle/*.sql`,
  committed and shipped in the image. CI regenerates and fails on any difference.
- `dist/migrate.js` (second tsup entry) opens one `pg.Client`, takes
  `pg_advisory_lock(7340412001)`, runs Drizzle's migrator on that same connection, unlocks and
  closes in `finally`, and exits 0 or 1. The API never migrates.
- `GET /health/ready` runs `SELECT 1`, then compares the applied migration set with the bundled
  journal; 503 `not_ready` with `database_unreachable` or `migrations_pending` otherwise.
- Tests: one container per run (Vitest global setup), a template database migrated once, and
  `CREATE DATABASE … TEMPLATE` per test file, dropped afterwards.

## Verification findings

- **V1 lock and migrator on one connection:** yes. `migrate(drizzle({ client }))` runs its
  `CREATE SCHEMA`, bookkeeping reads and the migration transaction on the given `Client`
  (Drizzle only checks out a new connection when handed a `Pool`). A process test holds the lock
  from another connection: the runner waits, then migrates once the lock is released. Two
  concurrent runners both exit 0 and the migration is recorded once.
- **V2 where applied migrations live:** `drizzle.__drizzle_migrations (id serial, hash text,
created_at bigint)`. `hash` is the SHA-256 of the SQL file; `created_at` is the journal's
  `when`. The migrator applies every bundled migration whose `when` is newer than the last
  recorded row, so readiness compares by `created_at` too: editing an applied file does not make
  the instance unready forever, and a database ahead of the build is reported as not ready.
- **V3 per-statement timeout:** both work against a real server with `pg_sleep`: the pool option
  `statement_timeout` (every statement on that pool) and, inside a transaction,
  `SELECT set_config('statement_timeout', $1, true)`, the parameterisable form of `SET LOCAL`.
  Both cancel with SQLSTATE 57014; the local setting is gone after the transaction on the same
  connection. Terminal writes in the generation ticket use the transaction-local form.
- **V4 UUIDv7:** `uuid` 14 exports `v7` (RFC 9562) and is maintained; Node 22's `crypto`
  only has v4. Ids are generated by the app; the version is not an ordering contract.
- **V5 testcontainers:** works locally on Windows with Docker Desktop and on GitHub's
  ubuntu-24.04 runners without setup. `pnpm test:unit` runs without Docker.

## Consequences

- Timestamps are returned at the database's precision (`2026-10-21T15:27:10.982364Z`). A list
  cursor carries the same value; with JavaScript's milliseconds, rows sharing a millisecond would
  be skipped or repeated, which a test covers.
- The list index is `DESC NULLS FIRST`, matching a plain `ORDER BY … DESC`; drizzle-kit's
  default `NULLS LAST` would not serve that ordering.
- Integration tests need Docker and run two files at a time to keep peak memory down on a laptop.
- Startup fails fast on bad configuration (catalog, enabled providers, default pair); a database
  that is down only makes the instance unready.
