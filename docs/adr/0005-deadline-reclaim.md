# ADR 0005: Deadline-bounded stale reclaim instead of leases and heartbeats

- Status: accepted
- Date: 2026-10-22

## Context

An answer is generated by an in-process job (ADR 0003). The database row of that answer says
`generating` until the job stores `completed` or `failed`, and the partial unique index allows
one generating turn per session. Several things can stop a job from ever storing that final
state:

- the upstream call hangs and never finishes;
- the process crashes or is killed, so the job and its memory are gone;
- the database is slow or unreachable just when the final state is written;
- the server shuts down while the answer is still being generated.

Without a rule for these cases the row stays `generating` forever: polling never ends, and the
session answers 409 `session_busy` to every new message. The system has to decide, from the
database alone, when a generating row is dead.

## Options considered

- **Leases with heartbeats:** the job renews a `lease_until` column every few seconds; anyone
  may take over or fail a row whose lease expired. This is the usual multi-worker design, but
  it costs a write per heartbeat per running answer, needs a lease column and a clock policy,
  and only pays off when another worker can resume the work, which a single process cannot.
- **A background sweeper:** a timer fails old generating rows every minute. It still needs a
  rule for "old", runs whether or not anyone looks, and is one more moving part to stop on
  shutdown and to reason about during a deploy overlap.
- **Deadlines plus lazy reclaim:** every attempt has a hard deadline, the final write has a
  hard budget, so a row still generating after deadline + budget + a grace has no live job by
  construction. Whoever touches the session next fails such a row.

## Decision

The last option.

- **Deadline.** Every attempt ends within `GENERATION_DEADLINE_MS` (180 s), counted on the
  process's monotonic clock from a reading taken immediately before the insert that sets
  `started_at = clock_timestamp()`. That reading happens earlier in real time than
  `started_at`, so the job always stops before `started_at + deadline` without ever comparing
  the two clocks. The worker computes the whole milliseconds left when it starts (the commit
  may have been slow); with none left it fails the turn as `llm_timeout` without calling the
  provider. Otherwise one timer per job, cleared when the job ends, aborts the generation, which
  is then stored as failed / `llm_timeout` with its partial text.
- **Terminal-write budget.** Storing the final state gets `TERMINAL_WRITE_BUDGET_MS` (10 s) in
  total. Each try is a short transaction with `SET LOCAL statement_timeout` set to the smaller
  of `TERMINAL_STATEMENT_TIMEOUT_MS` (3 s) and what is left of the budget, and the whole try,
  including getting a connection and committing, is raced against what is left. Failed tries
  are retried after 100, 200, 400 … ms, but a backoff that could not end within the budget is
  not started. When the budget runs out the job logs the assistant id, attempt and number of
  tries, releases its capacity, and leaves the row.
- **Stale reclaim.** A row still `generating` `GENERATION_DEADLINE_MS +
TERMINAL_WRITE_BUDGET_MS + RECLAIM_GRACE_MS` (180 + 10 + 50 = 240 s) after its `started_at`
  becomes failed / `interrupted`; partial text is kept. The comparison runs entirely on the
  database clock (`started_at < clock_timestamp() - threshold`). It runs inside the admission
  transaction right after the session lock, after the lock of `PATCH /sessions/:id`, and as a
  statement of its own before `GET /sessions/:id`, the message list and get-one. Later
  session-scoped endpoints (events, retry, delete) adopt the same entry point, `reclaimStale`.
  Usually it matches nothing; the partial unique index on generating rows serves it.
  Startup rejects a `RECLAIM_GRACE_MS` below `TERMINAL_STATEMENT_TIMEOUT_MS` + 1 s: after its
  deadline a live job may still wait one statement for a flush in flight before its terminal
  budget starts, and the second covers late timers. Every database call of a job carries a
  statement timeout (the history read and a flush one statement timeout, the history read no
  later than the deadline either; the terminal write and its read-back of the final state the
  budget), so a call the job stops waiting for, at its deadline or at a shutdown, is cancelled
  by the database within the shutdown wait and frees its connection.
- **Fencing covers the rest.** Every generation write carries `id + attempt + status =
'generating'`. A worker that wakes after its row was reclaimed (a paused process, a frozen
  event loop) matches no row on its next flush, aborts with reason `fenced` and writes nothing
  more.
- **Graceful shutdown** aborts every job with reason `shutdown`. A job whose answer is not
  finished stores failed / `cancelled` within the terminal budget; one that has its finish event
  stores `completed`. Closing waits a 1 s grace for providers to stop, one statement timeout for
  a flush still in flight and the terminal budget (14 s); the process's forced-exit timeout
  adds 4 s for closing the server and the pool (18 s in all).
  Rows not stored in time are reclaimed later. Waiting JSON clients receive the stored outcome.

## Consequences

- **The four-minute window.** After a crash, a turn still shows `generating` for up to
  240 s, and the session answers 409 until then. A client that polls sees `generating`, then
  `failed` / `interrupted`, and can send again (or retry, once retries exist).
- **Reclaim is lazy.** A session nobody touches keeps its dead row until somebody does. That
  is harmless: the row is only visible through the reads that reclaim it first.
- **Reads write.** Every session-scoped read issues one `UPDATE` that usually matches nothing.
  It takes no row locks unless it reclaims something.
- **The thresholds depend on configuration.** Raising the deadline or the budget raises the
  stale threshold with it, because it is derived at startup. A shorter `JSON_MAX_WAIT_MS` than
  deadline + budget is valid; the server logs a notice that JSON clients may get 202 for long
  answers.
- **A failed final write now answers 202**, not 500, to a JSON client waiting for it: the turn
  is honestly still unresolved, and polling ends once reclaim fails it.
- **Shutdown cannot guarantee the cancelled write** (the database may be the reason for the
  shutdown); reclaim is the backstop. A platform's stop grace period must exceed the 18 s
  forced-exit timeout (compose sets 20 s).
- **A deploy overlap stays correct.** The old process's jobs either finish, hit their deadline,
  or are fenced by a newer write; the new process reclaims whatever the old one left.

## Upgrade path (several API instances)

Deadline-based reclaim assumes nobody can resume a generation, which holds for a single
process. With several instances, or a queue of work, a row would carry a lease
(`owner`, `lease_until`) renewed by heartbeats, reclaim would test the lease instead of
`started_at`, and a background sweeper would release expired leases so that waiting work moves
on without a client touching the session. The fencing token (`attempt`) and the terminal-write
budget carry over unchanged.
